# receipt2csv コードレビュー

- 対象: `target/receipt2csv.py`, `target/receipt_ocr.swift`（仕様は `target/SPEC.md`）。`target/` は一切変更していない
- 実行環境: macOS 26.4.1 / Python 3.14.5 / PyMuPDF 1.28.0 / Pillow 12.3.0 / Swift 6.3.3
- 前提: 既存テスト19件はすべて成功し、同梱サンプル7件も期待値どおりに出る。つまり素直なレイアウトなら動く。以下はサンプルにない入力で見つけた問題
- 再現用ファイルはすべて `review/` にある
  - `python3 -B review/make_cases.py` … 再現入力を `review/cases/<ケース名>/` に生成する（PDF は PyMuPDF とサンプルと同じ内蔵 japan フォント、画像は Pillow とヒラギノで作成）
  - `sh review/run_all.sh` … 下記の全コマンドを実行し、結果を `review/results.txt` に保存する（本書の出力はここからの転記）
  - `python3 -B review/dump_text.py <ファイル>` … ツール自身の関数で、抽出前のテキスト（OCR 結果を含む）を行番号付きで表示する
  - `review/debug_ocr.swift` と `review/preprocess_like_tool.py` … 行をまとめる前の Vision の生座標を見るための調査用
- コマンドはリポジトリ直下で実行する。画像ケースは回転や余白を付けた合成画像で、実物のスマホ写真では試していない。Vision の認識結果は macOS のバージョンによって多少変わりうる

重大度の目安
- 高: よくある入力で、誤った値を警告なしに出す
- 中: 誤った値を出すが条件が限られる、またはよくある入力で項目が空になる
- 低: まれな入力や環境で、項目が空になるか行が消える

## 高

### 高-1 「値引合計」「8%対象合計」「合計点数」が合計行より上にあると、その数字を合計として出す

「合計」を含む行はどれも同じ順位の候補になり、同順位では一番上の行が採用されます。そのため、値引・税率ごとの小計・点数の行が本当の合計より上にあると、その数字が amount に入ります。警告は出ません。

```sh
python3 target/receipt2csv.py review/cases/amount_compound_total
```
入力（各PDFの金額まわり）
- `a_discount.pdf`: `小計 ¥1,500` / `値引合計 -¥200` / `合計 ¥1,300` / `お預り ¥2,000` / `お釣り ¥700`
- `b_tax_rate.pdf`: `8%対象合計 ¥540` / `10%対象合計 ¥1,100` / `合計 ¥1,640`
- `c_item_count.pdf`: `合計点数 3点` / `合計 ¥1,280`

実際の出力
```
file,date,amount,store
a_discount.pdf,2026-10-10,200,スーパーみどり
b_tax_rate.pdf,2026-10-10,540,スーパーみどり
c_item_count.pdf,2026-10-10,3,スーパーみどり
```
期待: 1300 / 1640 / 1280

原因
- `receipt2csv.py:51-52`: ラベル `合\s*計` は行のどこにあっても一致する。そのため「値引合計」「対象合計」「合計点数」も合計ラベルとして扱われる
- `receipt2csv.py:59`: 除外語の判定は、ラベルより前の部分にしか当てていない。しかも「値引・割引・対象・点数」は除外語に入っていない
- `receipt2csv.py:76-77`: `max((rank, -index, …))` なので、同順位なら一番上の行が勝つ。結果は行の並び順で決まり、`合計 ¥1,300` が `値引合計` より上なら正しく 1300 になる

### 高-2 写真が右上がりに1.5°以上傾いていると、次の行（現金＝お預り）の金額を合計として出す（1°では空になる）

傾いた写真では、同じ行にあるラベルと金額の高さがずれ、Swift 側で別々の行に分かれます。右上がりの場合は金額がラベルより上の行に並ぶため、「合計」の次の行は**一つ下の項目（現金）の金額**になり、それが採用されます。

```sh
python3 target/receipt2csv.py review/cases/ocr_tilt
```
`a_upright.png` はサンプル `06_lunch.jpg` と同じ内容の正立画像です。`b_rotate_+N` はそれを N° 反時計回り（右上がり）に、`-N` は時計回りに回転させたものです。

実際の出力
```
file,date,amount,store
a_upright.png,2026-10-07,980,定食処 あおば
b_rotate_+1.0.png,2026-10-07,,定食処 あおば
b_rotate_+1.5.png,2026-10-07,1000,定食処 あおば
b_rotate_+2.0.png,2026-10-07,1000,定食処 あおば
b_rotate_+3.0.png,2026-10-07,1000,定食処 あおば
b_rotate_-1.0.png,2026-10-07,980,定食処 あおば
b_rotate_-2.0.png,2026-10-07,980,定食処 あおば
b_rotate_-3.0.png,2026-10-07,980,定食処あおば
```
期待: すべて 980。1000 は「現金 ¥1,000」、つまりお預り額

OCR 後のテキスト（`python3 -B review/dump_text.py review/cases/ocr_tilt/b_rotate_+2.0.png` の抜粋）
```
  5| 小計
  6| ¥980
  7| 合計
  8| ¥1,000      ← 「現金」の金額
  9| 現金
```
Vision の生座標で見ると、「合計」は midY=0.3895、その金額 ¥980 は midY=0.4215 です。差 0.032 が閾値 0.012 を超えるため別の行になり、並び順で「合計」の直後に ¥1,000（midY=0.3032）が来ます。右下がり（-）で正しく出るのは、ラベルの直後にたまたま自分の金額が来るからです。

原因
- `receipt_ocr.swift:12-26`: 観測を midY の降順に並べ、行の先頭との差が 0.012 以下のものだけを同じ行にまとめている。傾きの補正も、ラベルと金額を横方向に対応付ける処理もない
- `receipt2csv.py:66-69`: ラベル行に金額がないとき、次の行が数字だけなら無条件にそれを採用する

### 高-3 正式な領収書の宛名（〜様／〜御中）を店名として出す

店名は「上から見て最初の、それらしい行」で決めています。「領収書」の次にある宛名の行は除外されないため、**支払った側（自分や自社）の名前**が store に入ります。宛名入りの領収書は経費精算で最も一般的な書式です。

```sh
python3 target/receipt2csv.py review/cases/store_addressee
```
入力
- `a_formal_sama.pdf`: `領収書` / `山田 太郎 様` / `¥12,100-` / `但し 書籍代として` / `2026年10月1日` / `上記正に領収いたしました` / `まるいち書店` / `東京都架空区1-2-3`
- `b_onchu.pdf`: `領収書` / `株式会社テスト 御中` / `2026/10/01` / `合計 ¥1,100` / `まるいち書店`

実際の出力
```
file,date,amount,store
a_formal_sama.pdf,2026-10-01,,山田 太郎 様
b_onchu.pdf,2026-10-01,1100,株式会社テスト 御中
```
期待: store はどちらも「まるいち書店」。a の amount は 12100（空になる理由は中-6）

原因: `receipt2csv.py:80-103`。最初に文字を含む行をそのまま返し（`:100-102`）、「様」「御中」を含む行を除外していない。発行者名が下部にある書式も考慮されていない

### 高-4 行の間隔が画像の高さの約1.2%より狭いと上下の行が1行に結合され、金額が空になり、店名に住所が混ざる

同じ行とみなす閾値が「画像の高さに対する比率 0.012」に固定されています。行数の多いレシートや、机に置いて余白ごと撮った写真では、上下の行が1行にまとめられます。「小計 合計 ¥8,605」のように結合されると、ラベルより前に「小計」があるため行ごと除外され、金額が空になります。店名は住所とつながります。

```sh
python3 target/receipt2csv.py review/cases/ocr_row_merge
```
どちらも同じ37行のレシートです。`a_on_desk.png` はレシートが画像の高さの45%を占めるよう余白付きで置いた写真、`b_cropped.png` はぴったり切り抜いたものです。

実際の出力
```
file,date,amount,store
a_on_desk.png,2026-10-10,,東京都架空区1-2-3 スーパーみどり 中央店
b_cropped.png,2026-10-10,8605,スーパーみどり 中央店
```
期待: どちらも 8605 / スーパーみどり 中央店

OCR 後のテキスト（`python3 -B review/dump_text.py review/cases/ocr_row_merge/a_on_desk.png` の抜粋）
```
  0| 東京都架空区1-2-3 スーパーみどり 中央店
  1| 2026年10月10日 18:32 商品01 ¥137
  2| 商品03 商品02 ¥174 ¥211
 17| 商品30 ¥8,605 ¥410
 18| 小計 合計 ¥8,605
 19| お預り お釣り ¥11,395 ¥20,000
```
行の間隔は 40px ÷ 画像の高さ 3467px ≈ 0.0115 で、閾値 0.012 を下回ります。切り抜いた画像（≈0.026）では正常です。品目数だけを 27〜32 に変えた5枚（`review/cases/ocr_row_merge_more`）でも、4枚で金額が空、3枚で店名に住所が混ざりました。計算上、余白がなくても約84行を超えるレシートは同じ状態になります。

原因
- `receipt_ocr.swift:21`: `abs(last.y - y) <= 0.012`。文字の高さではなく、画像全体の高さを基準にした固定の閾値になっている
- `receipt2csv.py:59`: 結合された行では、ラベルの前に「小計」があるため合計行ごと除外される。店名は結合された行がそのまま返る（`:100-102`）

## 中

### 中-1 英語レシートの「SUB TOTAL」「Sub-Total」「TOTAL TAX」を合計として出す（SUB TOTAL の除外が効いていない）

```sh
python3 target/receipt2csv.py review/cases/amount_english_subtotal
```
入力
- `a`: `SUB TOTAL ¥300` / `TAX ¥30` / `TOTAL ¥330`
- `b`: `Sub-Total ¥300` / `Tax ¥30` / `Total ¥330`
- `c`: `SUBTOTAL ¥1,000` / `TOTAL TAX ¥100` / `TOTAL ¥1,100`

実際の出力
```
file,date,amount,store
a_sub_total.pdf,2026-10-10,300,Blue Bottle Cafe
b_sub-total.pdf,2026-10-10,300,Blue Bottle Cafe
c_total_tax.pdf,2026-10-10,100,Blue Bottle Cafe
```
期待: 330 / 330 / 1100

原因
- `receipt2csv.py:52`: `\bTOTAL\b` が「SUB TOTAL」「Sub-Total」「TOTAL TAX」の中の TOTAL にも一致する
- `receipt2csv.py:50`, `:59`: 除外語 `SUB\s*TOTAL` は、ラベル（TOTAL）より前の部分＝`"SUB "` にしか当てていない。このため一致することがなく、実質的に効いていない
- `receipt2csv.py:64`: 税額を切り捨てる処理は日本語の「消費税・税額」などだけで、英語の TAX には効かない
- 同順位なので一番上の行が勝つ（`:76-77`）。既存テストは空白なしの `SUBTOTAL` しか確認していない

### 中-2 通貨記号（¥・円）がないと、行内の最初の数字（点数など）を合計として出す

```sh
python3 target/receipt2csv.py review/cases/amount_unmarked_first_number
```
入力
- `a_backslash_yen.pdf`: `合計 3点 \1,280`。Shift_JIS の環境で作られた PDF では、円記号がバックスラッシュ（U+005C）で入っていることがある
- `b_items.pdf`: `TOTAL (2 items) 1,500`
- `c_count_then_next_line.pdf`: `合計 3点` の次の行に `¥1,280`

実際の出力
```
file,date,amount,store
a_backslash_yen.pdf,2026-10-10,3,スーパーみどり
b_items.pdf,2026-10-10,2,Blue Bottle Cafe
c_count_then_next_line.pdf,2026-10-10,3,スーパーみどり
```
期待: 1280 / 1500 / 1280

原因
- `receipt2csv.py:72-73`: 通貨記号付きの数字がないと `matches[0]`、つまり行内で最初の数字を採る。金額は普通右端にあるのに、左端の点数が選ばれる
- `\` は NFKC で ¥ に変換されず、`:54` の通貨記号にも含まれていない
- c では、ラベル行に「3」があるため次の行の ¥1,280 を見に行かない（`:66`）

### 中-3 金額の後ろに空白と数字が続くと、数字をつなげた大きな金額を出す

```sh

```

## 低

### 低-1 背景が透明なPNGは全項目が空になり、警告も出ない

```sh
python3 target/receipt2csv.py review/cases/image_transparent_png
```
`a_transparent.png` は白地を透明にしただけの画像（文字は黒）で、`b_same_on_white.png` はそれを白地に重ねたものです。

実際の出力（標準エラーには何も出ない）
```
file,date,amount,store
a_transparent.png,,,
b_same_on_white.png,2026-10-07,980,定食処 あおば
```
期待: a も 2026-10-07,980,定食処 あおば

原因
- `receipt2csv.py:158`: `convert("RGB")` はアルファを捨てるだけなので、透明な部分には保存されている色（この画像では黒）が残る。結果は黒地に黒文字になり、Vision が何も読めない
- OCR の結果が空でも警告しないため、利用者は原因に気付けない。実際のアプリが書き出した透過PNGで起きるかは未確認

### 低-2 Shift_JIS／EUC-JP のロケールでは、OCR を通るファイル（画像・スキャンPDF）がすべて空になる

```sh
LC_ALL=ja_JP.SJIS python3 target/receipt2csv.py target/samples
```
実際の出力。CSV は UTF-8 で出ます。標準エラーは Shift_JIS で出るので、UTF-8 に変換して載せています。
```
file,date,amount,store
01_cafe.pdf,2026-09-03,1280,カフェ ミドリ堂
02_stationery.pdf,2026-09-14,1573,文具のサクラ屋
03_books.pdf,2026-10-01,12100,まるいち書店
04_taxi.png,,,
05_parking.png,,,
06_lunch.jpg,,,
07_scanned.pdf,,,
警告: 04_taxi.png を読めません: 'shift_jis' codec can't decode byte 0x8c in position 41: illegal multibyte sequence
（05〜07 も同様）
```
`LC_ALL=ja_JP.eucJP` でも同じく4件が空になります（`'euc_jp' codec can't decode …`）。

原因: `receipt2csv.py:135-137`。Swift のプログラムは UTF-8 で JSON を書くのに、`subprocess.run(..., text=True)` はロケールの文字コードで読む。標準出力は UTF-8 に固定しており（`:188-189`）、ASCII 環境のテストもあるので、非 UTF-8 の環境でも動かす意図はあったと思われる。ただし OCR の受け取りが漏れている

### 低-3 リンク切れのシンボリックリンクは、行も警告も出ずに消える

```sh
python3 target/receipt2csv.py review/cases/broken_symlink
```
入力: `a_ok.pdf` と、存在しないファイルを指す `b_link_to_missing.pdf`

実際の出力（標準エラーは空）
```
file,date,amount,store
a_ok.pdf,2026-10-01,1100,まるいち書店
```
期待: 仕様「読めないファイル…があっても止めない。そのファイルの行は出し、取れなかった項目は空にする」に従い、`b_link_to_missing.pdf,,,` の行と警告を出す

原因: `receipt2csv.py:174-175`。`path.is_file()` はリンク切れで False になるので、一覧から何も言わずに落ちる。読み取り権限のないファイルは警告付きの空行になり（確認済み）、扱いが食い違っている

### 低-4 1ページでも OCR に失敗すると、他のページで取れた文字も捨てて全項目空になる

```sh
env PATH=/var/empty "$(command -v python3)" target/receipt2csv.py review/cases/pdf_blank_second_page
```
`PATH` から swiftc を外して、Swift（Xcode Command Line Tools）の無い Mac を模擬しています。`a_one_page.pdf` は文字入りの1ページ、`b_two_pages.pdf` は同じ1ページの後ろに白紙のページを足したものです。

期待: b も1ページ目から 2026-10-01,1100,まるいち書店

原因: `receipt2csv.py:147-155`。文字のないページ（裏面の白紙など）でも OCR を呼び、その例外がファイル全体の失敗として扱われる（`:194-198`）。実際に CLT の無い Mac では未確認で、PATH の操作による模擬で確かめた

### 低-6 幅の小さい画像を上限なしで拡大するため、時間とメモリを大量に使う

## 問題なしと確認したもの

- 既存テスト19件、サンプル7件
- 大文字の拡張子、サブフォルダの無視、空フォルダ
- 入力フォルダが無い・ファイルを指定した場合は、エラー終了して traceback を出さない
- 壊れた PDF や画像、パスワード付き PDF（`review/cases/ok_encrypted_pdf`）、読み取り権限のないファイル → 警告付きの空行を出して処理を続ける
- ラベル列と金額列を別々に描いた表形式の PDF（`review/cases/ok_pdf_columns`）→ PyMuPDF の並べ替えで正しく 1257 になる。「次の行の数字を拾う」処理が PDF でずれる心配は、確認した範囲ではなかった
- 16bit グレースケールの PNG（`review/cases/ok_image_16bit_png`）
- 出力先が入力ファイル自身やそのハードリンクのときは、エラーで拒否する。`| head -1` でパイプを閉じても traceback は出ない

## 未確認

- Linux などで、UTF-8 として不正なバイト列のファイル名があると、CSV 書き込み時の UnicodeEncodeError を `except OSError`（`:203`）で捕まえられず、異常終了する可能性がある。macOS（APFS）ではそのような名前のファイルを作れないため確認できていない
- 実物のスマホ写真での傾きや余白の影響（合成画像でのみ確認）

## 不具合ではないが気になる点（仕様判断・好み）

- 返品レシート `合計 -¥1,280` は符号が落ちて `1280` になり、支払いとして計上されてしまう（`review/cases/note_refund_and_appledouble`）。仕様の「数字だけ」にマイナスを含めるか決めておくべき
- 外付けドライブなどで macOS が作る `._xxx.pdf`（AppleDouble）も対象の拡張子なので、警告付きの空行として出る（仕様どおりだが紛らわしい）
- CSV の改行は CRLF（csv モジュールの既定）。BOM なしの UTF-8 なので、Excel でそのまま開くと文字化けする（どちらも仕様の範囲内）。店名が `=` `+` `-` `@` で始まると、表計算ソフトが数式として解釈しうる（Excel での挙動は未確認）
- Swift を実行のたびにコンパイルし、一時ファイルはスクリプトの隣に作る（README に記載あり）。インストール先が書き込み不可だと、画像は全件読めない
- テストは素直なレイアウトしか扱っておらず、今回の指摘はどれも既存テストでは検出できない。`extract_amount` の順位付け（`:75` の三項演算子の入れ子）や、店名抽出の除外用正規表現の羅列は、条件を足すたびに副作用（中-5 の「100円」）が出やすく、読みにくい

## まとめ

- 指摘: **16件**（高4・中6・低6）。ほかに、仕様判断が必要な点を1件（返品の符号）
- 実務で使ってよいか: **このままでは不可**。値引合計のある普通のレシート、少し傾いた写真、宛名入りの領収書といった、日常的な入力で金額や店名を**空ではなく誤った値として、警告なしに**出します。そのまま経費精算や会計に取り込むと誤計上になります。使うなら、全行を原本と突き合わせる前提の下書き作りに限るべきです
